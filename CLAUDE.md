# Notes for Claude

## Prototype version number

The prototype shows its version in the bottom-left corner: the `.proto-ver` element in `src/prototype.html` (its text and its `aria-label`). Format: `vMAJOR.MINOR` or `vMAJOR.MINOR.PATCH`.

Every update the user asks for bumps the version before it is committed and published. Claude decides whether the update is small or bigger:

- **Small → patch** (v1.3 → v1.3.1 → v1.3.2): tweaks and fixes to what already exists, such as copy edits, spacing, sizes, colours, alignment, a bug fix, or polishing one element.
- **Bigger → minor** (v1.3.2 → v1.4): new or reworked behaviour or layout, such as a new screen, state, variant, feature or interaction, a restructured layout, or a change that spans several screens. The patch number is dropped: v1.4, not v1.4.0. After v1.9 comes v1.10.
- **Major** (v1.x → v2.0): only when the user explicitly says so (e.g. "increase to v2"). Minor and patch reset: v2.0.

Changes that don't touch the prototype itself (README, these notes) don't bump the version.

Start the commit subject with the new version (e.g. `v1.3.1: …`) and mention it in the reply.

## Variant C visibility

Variant C ("picture on top") can be hidden without removing it. `SHOW_C` in `src/prototype.html` controls it: `true` shows its button in the More options panel (bottom-right corner, Flows view) and lets `#c` open it (current state); `false` hides that row and sends `#c` links and a remembered C choice to A, while all of C's markup, styles and logic stay in place. When hiding it, also add a "hidden for now" note to C in the README; when showing it, remove that note.

## Hidden decorations in the 3D look

The 3D look's resume fragments (the four faded pages in the side margins of the method screen) are hidden, not removed. `SHOW_3D_PAPERS = false` in `src/prototype.html` adds `no-papers` to the backdrop, which hides them; their markup and styles stay in place. To bring them back, set `SHOW_3D_PAPERS = true` (and update the README's look description); nothing else needs to change.

## The six groups

## The four flows

- Every URL follows one of four flow templates (`FLOW_T`, from the user's flow board in Figma): 1 intent collection → feature personalization → data processing → processing state → destination (Skip personalization → dashboard); 2 personalization → processing → state → destination; 3 processing → state → destination; 4 destination. Sign up, Log in or a landing page can come first (`entry`). The user's idea: a new URL only pairs to one of the four and fills in its own screens. The spec is the user's doc "URLs by flow and situation" (https://claude.ai/artifact/7tifXYJtNj2VjvziJmzwEe): every URL's destination, what it needs and its flow for New, no CV · New + CV (a landing page) · Logged in, no CV · Logged in + CV; check it before changing a run. The model: the person sees only the steps for what is missing, in the order goal → account → CV → data → loading → destination, and the flow number follows (1 goal screen, 2 a CV step or setup, 3 only loading, 4 nothing). The App runs are written in `FEATURES` (`needsCv(id, …)` gives a page that needs a CV its with-CV run and its `-new` run with the method screen first); `lpVariant(base, cv, data)` makes the landing-page runs from them (`lp-<id>-cv|nocv[-data]`): a landing page collects a CV only for the URLs in `LP_CV` (the user's rule; never the resume-building URLs: New resume, a template, Create Resume with AI, since someone there has no resume yet, and a landing page's upload block leads to Upload resume), none for `LP_NONE` (Log in, latest-resume, guest editor); with a CV and nothing to fill, Sign up · CV attached → the upload modal (`LP_UPM`; LinkedIn imports the profile) → straight on (Flow 3); with a setup still to fill, the setup comes first and the upload modal opens the processing (Flow 2, in the template's order); `data` (a feature's `given`: the job details, the role…) skips the form (Flow 3). Tailor and Translate are one landing-page flow each (the user's rule): a landing page that takes the CV takes their data too (the job, the language), so with a CV they only have the run with the data. The hand-made landing runs (`landing-cv`, `landing-ats`, `landing-tailor` and `landing-jobs-tailor` with the job, Translate's two, which always have the language) carry `lp: true`.
- `FEATURES` pairs every URL with its flow: `flow`, `group` (the URL checklist's group, kept as data), `title`, `path` (`url` when the shown URL has a placeholder such as `{template}`), `entry`, `prep` (the feature personalization), `process` (default: the shared processing wireframe worded by `verb` and `psteps`; `false`: none, and no processing state either, like the job board's search), `dest` (the destination), `noun` (what the result is called), `cv` (start with or without a CV; without it the dock's CV choice decides, `pmCvOn` / `runsWithCv`), `data` / `given` (a landing page gave the feature's data; `given` names it), `guest` (no account: the run is Flow 4, straight into the app; the app menu, Download, Upgrade, AI and Resume Tailoring open the sign-up pop-up, `signupPop`, and Sign up or Log in returns them through `guestBack`: the user's rule), `appOff` (not offered from the app: every feature's run without a CV that needs one, `APP_CV_ONLY`, since the app never goes through resume creation; Tailor's two are copies of the either-way runs; they stay as landing-page bases and `redo` runs), `state` (the feature's own processing state instead of the shared `WIRE.state`), `redo` (Flow 3: the feature whose run "Change the input" switches to, since the input came before the run). `prep`, `process` and `dest` are steps from the `S.*` helpers (`wire`, `route`, `wireTool`, `cv` (a tool's CV: the method screen; `toolPrep`), `upm` / `buildFor` (the CV made there: the upload modal or the building screen, both in `cvMade(path)`; a run goes on from whichever the person took), `trlRun` (Tailor's card as processing and state), `screen`, `build`, `editor`, `dash`, `docs`, `tool`, `auth`, `upgrade`, `latest`, `jobs`, `dest`), or a function returning them when they depend on the CV (`toolPrep`). `buildFlow(f)` lays them out in the flow's stages. To add a URL, add a `FEATURES` entry (and a `ROUTES` entry if its screen should be in the URLs list).
- Processing moves on by itself (`processDone`; the building screen through `afterBuild`, which hands over to the run only when the building screen is its processing; the upload modal waits for Continue, `upmDone`, which goes to the screen that asked (`cvNext`), else the run's next step (skipping the building screen, its `alt`, and result steps) or the editor; Back after a failed upload in a run with no personalization (Flow 3) starts the `redo` feature). The Upload and LinkedIn import screens' runs use `upmRun(path)`: the modal as processing (`S.route(…, 'progress')`) and its result as the processing state (`'progress-end'`). The dock's Ends (`setResult`) sets `procResult`: Completed skips the processing state and goes straight to the destination; Failed and Error show it (`WIRE.state`), with a way back to the personalization (`redo` for Flow 3) or the processing; a run's building screen set to fail stops early without celebrating (`runBuilding`). Generate work experience / objective are section writers: `SECTION_AS` words their building screen, `withSection` changes only that section when there is a CV, and they end in the editor at that section (`openEditorAt`; a dest step can do the same with `S.editor(label, path, sec)`).
- Flow 1's goal screen switches the run to the goal picked (`flowGoal`). A screen's own button moves a run on with `flowOn()` / `flowNext()`.
- The run dock (`#proto-dock`, bottom right beside the More options button) is how a flow is picked and run, in one row (the user's wish: no settings buried in a panel). It works like the app will (the user's idea: the URL says where the person ends up, a resolver shows only the steps whose data is missing): Open (`pmKey`, a feature's `path`; `PM_URLS`, one entry per URL in the six `KINDS` groups), From (`pmFrom`: `signup`, `app`, `lp`, `guest` (`FROM`), from `fromOf(f)`: Flow 1 features are Sign up and live only under `/register/` (`dockPath`: the user's rule, the goal runs are branches the goal screen picks, never their tools' URLs), `lp` ones Landing page (every URL but /register/ has both CV choices there), guest features Guest, the rest App; choices a URL doesn't have are dimmed), CV (`.dk-cv`, `pmCvOn`; dimmed when the URL's entries for that arrival decide it, `pmCvFree`), Data (`.dk-data`, `pmDataOn`, `pmDataFree`; `pmPickOf(list, cv, data)`), Ends (`ENDS`, the processing result, `setResult` / `procResult`) and Run (`.dk-run`: `data-feature`, `startFeature`; it reads "Flow N", with the flow's name and step count (`pmSteps`) as its tip, and gets a green ring while that run is going). `pmFeature()` resolves them to one `FEATURES` entry. Each list (`ddHTML`, `.dk-list`) is a fixed-position listbox that opens upwards (below when there's more room) and scrolls inside itself (`ddOpen` / `ddClose` / `ddActive` / `ddPick`); never the native select, which fills a Mac's screen. `renderDock` draws it once and `dockUpdate` changes it in place (no redraws: it must not jump). On phones it is its own row above the bottom one, with short labels (`.dk-short`: Landing, Done, ▶ N) and no captions, and `#device::after` is a spacer as tall as the dock, the flow bar and the note, so every screen scrolls clear of them. The flow bar and the wireframe note sit above it. The user wants it minimal: no intro text. Starting or switching a run (`startFeature`, `flowGoal`) moves the dock to it (`pmShow`). Every feature must stay reachable from the dock: one entry per path, arrival and CV.
- The More options panel has two views (`setPmTab`): Flows (the Flow checker switch, `renderFlowsPanel`, then Look and variant C) and URLs (`#pm-routes`, every `ROUTES` entry; a screen opened from there has the dock's CV and ends a run it isn't part of). With no run going, the dock's CV switch is the person's CV: toggling it calls `setCv`, and `setCv` moves it. The Flow checker switch (`checkerOn`, remembered as `kr-flow-checker`; `setChecker`, `startChecker`) starts a Flow 1 run on Sign up; `checkerAdopt(path)` (from `setHash`, and `openDashboard`) makes whatever the person opens in the app its own App run once the current run has none of that screen or has reached its destination (and not for the dashboard after Skip personalization); Restart and loading start on Sign up while it's on. The bar groups the run's dots by stage.
